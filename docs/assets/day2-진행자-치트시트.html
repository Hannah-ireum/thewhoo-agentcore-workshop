Lab 5. Runtime 배포 45분

목표: HTTPS 엔드포인트가 생기고, 다른 시스템이 SigV4 로 호출할 수 있다.
🗣️ 왜 Lambda 가 아닌가 (3가지)

1. 세션 유지 — 에이전트 대화는 상태가 있습니다. Lambda 는 stateless 라 세션마다 외부 저장소가 필요합니다.

2. 긴 실행 — 멀티턴 + 도구 호출이 이어지면 15분을 넘길 수 있습니다.

3. 관측 자동 연결 — CloudWatch Logs·X-Ray·Transaction Search 를 배포가 알아서 붙입니다.

🗣️ 이번엔 IaC 라는 점을 짚으세요

"새 CLI 는 '배포 스크립트' 가 아니라 프로젝트 전체를 JSON 으로 선언하는 방식입니다. CDK 가 CloudFormation 으로 바꿔 적용합니다."

"그래서 좋은 점 — remove 후 deploy 하면 정확히 되돌아갑니다. 손으로 만든 리소스는 이게 안 되죠."

📊 지표 하나하나 읽는 법 — "이 숫자가 무슨 뜻인가"

고객이 "그래서 이 그래프를 어떻게 봐야 하나요" 라고 물을 때 쓰는 표입니다. 각 지표마다 ① 무엇을 재나 ② 정상 범위 ③ 이상하면 무슨 뜻인가 를 짚으세요.

지표무엇을 재나정상이상하면
Invocations Runtime 이 받은 요청 수 (분당) 트래픽만큼 갑자기 0 → 엔드포인트 장애 또는 클라이언트가 안 부름. 급증 → 재시도 폭주 의심 (⑦ 로그 확인)
UserErrors 4xx — 클라이언트 잘못 (잘못된 요청·인증 실패) 0 올라가면 호출하는 쪽 문제. payload 스키마·SigV4 서명·세션 ID 길이를 봅니다
SystemErrors 5xx — 서버(내 코드·권한) 잘못 0 ⭐ 가장 위험한 신호. 대개 권한 부족이거나 코드 예외. 즉시 ⑦ 로그 → Observability span 으로 내려갑니다
Throttles 계정 한도 초과로 거절된 요청 0 동시 세션·TPS 한도 초과. 병렬 요청을 줄이거나 Service Quotas 증가 요청
Latency P50 중간값 — 절반은 이보다 빠름. 평범한 사용자 체감 이 에이전트는 수 초대 P50 자체가 오르면 전체가 느려진 것 — 모델 변경·프롬프트 증가·KB 지연
Latency P95 / P99 느린 5% / 1%. 최악의 경험 P50 의 2~3배 이내 ⭐ P50 은 그대로인데 P99 만 뛰면 "대부분 빠른데 일부가 심하게 느리다" — 이 에이전트에서는 서브에이전트를 몇 개 탔는지 · Gateway 도구를 몇 번 불렀는지에 따라 갈립니다
Sessions 대화 세션 수 (사용자 수에 가까움) Invocations 보다 적음 ⭐ Invocations ÷ Sessions = 평균 턴 수. 이 값이 1 에 가까우면 멀티턴이 안 쓰이고 있다는 뜻 — Memory 투자가 낭비일 수 있습니다
input_tokens 모델에 새로 보낸 토큰 (⚠️ 캐시된 건 제외) 캐시 ON 이면 작아야 정상 ⭐ 캐시를 켰는데 이 값이 크면 캐시가 안 듣는 것
output_tokens 모델이 생성한 토큰 답변 길이만큼 비용의 큰 부분 (출력이 입력보다 단가가 높음). 급증하면 답변이 장황해진 것
cache_read_input_tokens 캐시에서 재사용한 토큰 2회차부터 커짐 0 이면 캐시 미동작. TTL(5분) 만료 또는 프롬프트가 매번 바뀌는 것
Cache Hit Ratio cache_read ÷ (input + read + write) 20~40% (실측 29%) ⭐ 평소 대비 급락이 신호입니다 — system prompt 에 시각·랜덤값 같은 가변 요소가 들어가 캐시가 깨진 것. 절대값이 낮은 건 정상 (Haiku 3개는 캐시 대상이 아님)
CPUUsed-vCPUHours
MemoryUsed-GBHours		 컨테이너 자원 사용량 (누적) 워크샵 중엔 비어 있음 최대 60분 지연됩니다. 실서비스에서는 OOM·throttle 의 조기 신호이자 청구 추정 근거

⚠️ 참가자가 반드시 묻는 3가지 — 먼저 말해두세요

질문답
"에러가 0 인데요?" 정상입니다. 잘못된 payload 도 컨테이너까지 와서 app.py 가 "메시지를 입력해주세요" 를 정상 응답(200) 으로 돌려줍니다. 버그가 아니라 의도된 방어 설계입니다. 대신 대가가 있습니다 — 입력 오류가 metric 에 안 보입니다. 추적하려면 custom metric 을 직접 올려야 합니다. 이 trade-off 를 아는 것이 이 Lab 의 포인트입니다.
"Latency 선이 끊겨요" 장애가 아닙니다. CloudWatch 는 데이터 없는 구간을 잇지 않습니다. 워크샵 트래픽이 연속적이지 않아 호출 없는 구간마다 빈칸이 생깁니다. 시간 범위를 넓히면(3h→12h) 메워지는 것을 즉석에서 보여주면 바로 납득합니다.
"대시보드가 안 변해요" 가장 흔한 원인은 지연이 아니라 시간 범위 설정입니다. 우상단 시간 범위를 3h 로 바꾸고 Refresh 를 먼저 시키세요. 지연은 ①②③ 1분 / ④⑤ 2~5분 / ⑥ 최대 60분 / ⑦ 수십 초.

Lab 8. Evaluations 30분

목표: 답변 품질을 점수로 만들고, 회귀를 자동으로 잡는다.
🗣️ 왜 필요한가 — 이 한 문장

"Lab 6·7 까지는 양적 신호만 봤습니다 — 호출 수, 지연, 토큰. 그런데 '답변이 좋아졌나 나빠졌나' 는 하나도 알 수 없습니다."

"LLM 앱은 코드를 안 바꿔도 품질이 변합니다. 그래서 골든셋 — 매번 똑같이 던지는 고정 질문 세트가 필요합니다."

이건 CI/CD 안에서 도는 평가입니다

유형언제이 워크샵
On-demandPR 게이트 · 골든셋 회귀✅ 실습 본체
Batch배포 전후 비교, 정기 감사 (비동기·대규모)명령만 소개
Online운영 트래픽 지속 감시개념·링크만
🗣️ Online 이 골든셋에 못 쓰이는 이유 (좋은 질문이 나옵니다)

"운영 트래픽에는 정답이 없습니다. 공식 문서도 그 이유로 못 쓴다고 적고 있고, API 에 정답을 넘길 필드 자체가 없습니다."

"그래서 정답 있는 회귀 테스트 = On-demand, 정답 없는 운영 감시 = Online 으로 갈립니다. 실서비스는 둘 다 씁니다."

진행 순서

# 1) 5턴 대화로 trace 만들기 (SESSION_ID 는 33자 이상)
# 2) 인덱싱 대기 — 2~5분 (배포 직후 첫 trace 는 ~10분)
agentcore run eval --session-id "${SESSION_ID}" \
  --evaluator "Builtin.Helpfulness" \
  --evaluator "Builtin.GoalSuccessRate"
🛑 Builtin.ToolSelectionAccuracy 는 넣지 마세요

실환경에서 이 오류로 실패합니다:

Error: The evaluation target contains spanIds that do not exist
in the provided data. Missing spanIds: {'fa0b48931de2eb53', ...}

5분 더 기다려도 같은 spanId 가 그대로 나오므로 인덱싱 지연이 아닙니다. 도구 선택을 보려면 expected_trajectory 기반 Builtin.Trajectory*Match 를 쓰세요 — 프로그램적으로 채점하므로 이 문제가 없고 비용도 0 입니다.

📊 평가 결과 읽는 법 — "이 점수가 무슨 뜻인가"

aggregateScore : 0.932        ← 이 evaluator 의 전체 평균
sessionScores[] : turn 별 결과
  ├ traceId     : 이 turn 의 trace ID   ← ⭐ 답변 본문을 찾는 열쇠
  ├ value       : 0~1 정규화 점수
  ├ label       : 등급명
  └ explanation : judge 가 그 점수를 준 이유
tokenUsage      : judge LLM 이 쓴 토큰  ← 평가 자체의 비용
⚠️ 먼저 짚을 것 — 점수만 보면 안 됩니다

value 보다 explanation 이 중요합니다. 점수는 "몇 점" 이고, explanation 은 "왜 그 점수인지" 입니다. 회귀를 고치려면 후자가 필요합니다.

evaluator 별로 무엇을 재는가

evaluator재는 것낮으면 무슨 뜻인가
Builtin.Helpfulness
judge LLM		 답변이 사용자 목표 달성에 도움이 됐나 질문에 정면으로 답하지 않았거나, 정보가 부족·장황함. 등급: Above And Beyond / Very Helpful / Somewhat Helpful …
Builtin.GoalSuccessRate
judge LLM		 골든셋의 assertions 를 만족했나 (정답 대조) ⭐ 회귀 게이트의 핵심. 이게 떨어지면 "요구한 내용을 빠뜨렸다" 는 뜻. verdict: Yes/No 또는 SUCCESS/FAILURE
Builtin.Correctness
judge LLM		 expected_response 와 사실이 일치하나 KB 에서 잘못된 문서를 끌어왔거나 환각
Builtin.Trajectory*Match
프로그램 · 비용 0		 도구를 올바른 순서로 불렀나 Orchestrator 가 엉뚱한 도구를 골랐거나 순서가 틀림. 프롬프트·도구 설명을 손볼 신호

점수 구간을 어떻게 해석하나

value판단진행자가 할 말
1.0✅ 만족"요구한 내용을 다 담았습니다"
0.8~0.99✅ 통과 · 흠집 있음⭐ explanation 을 읽어주세요. judge 가 구체적 결함을 지목했습니다 — 여기가 개선 포인트입니다
0.5~0.79⚠️ 경계"통과했지만 반복되면 프롬프트를 손봐야 합니다"
< 0.5🛑 게이트 실패"이건 회귀입니다. traceId 로 내려가 원인을 봅니다"

게이트 기준은 run-golden-eval.py 의 DEFAULT_GATE 에 있습니다 (Helpfulness ≥ 0.5, GoalSuccessRate = Yes). value 는 API 가 이미 0~1 로 정규화해 주므로 환산이 필요 없습니다.

✅ 실측 예시로 시연하세요 — 이게 가장 설득력 있습니다

실제 결과에서 5턴 중 한 턴이 0.83 이 나왔습니다. judge 의 explanation 을 보면:

"The product ID WHOO-00101 is actually the 천기단 화현 크림, not the 아이크림 as stated in the response header…"

즉 judge 가 답변 헤더의 상품명 오류를 잡아냈습니다. 재고·가격·프로모션은 다 맞았지만 라벨이 틀려서 1.0 이 아니라 0.83 을 준 것입니다.

이걸 보여주면 "LLM 이 채점한다" 는 말이 실감됩니다 — 사람이 놓칠 수 있는 디테일을 찾아냈으니까요.

점수가 낮을 때 보는 순서

  1. explanation 먼저 — 대부분 여기서 원인이 드러납니다
  2. traceId 로 실제 답변 확인 — 콘솔 Observability 또는 agentcore traces get
  3. 같은 질문 재실행 — 일관되게 낮으면 코드·프롬프트 문제, 들쭉날쭉하면 모델 변동성
⚠️ 오탐을 회귀로 착각하지 않게

LLM-as-Judge 는 같은 답변에도 점수가 조금씩 달라집니다. 1건 FAIL 로 release 를 막지 말고, 같은 시나리오가 반복해서 떨어질 때 회귀로 판정하세요.

반대로 Trajectory*Match 는 프로그램 채점이라 결정적입니다 — 이게 FAIL 이면 확실한 회귀입니다. 게이트에서 더 신뢰할 수 있습니다.

⚠️ 참가자가 반드시 묻는 2가지

질문답
"AI 답변 본문은 어디서 봐요?" 평가 결과 JSON 에는 없습니다 — judge 채점만 담깁니다. traceId 가 열쇠입니다 (sessionId 는 턴마다 같고 traceId 가 다름).
시연은 콘솔로 — GenAI Observability → Sessions → 그 trace → invoke_agent span → 우측 Input / Output. "점수 0.83" 에서 실제 문장까지 내려가는 흐름이 설득력 있습니다.
"explanation 이 영어네요?" Builtin.* 의 판정 프롬프트가 영어 고정입니다. 점수는 한국어를 정확히 이해하고 산출됩니다 — 실측에서 judge 가 WHOO-00101 을 아이크림으로 잘못 라벨한 것을 잡아내 1.0 대신 0.83 을 줬습니다.
한국어 설명이 필요하면 agentcore add evaluator --instructions 로 custom evaluator 를 만듭니다. 단 점수 체계가 달라져 과거 비교가 안 되므로, 회귀 게이트는 built-in 유지 + 보고용만 별도로.
🗣️ 골든셋 작성 원칙 — 실무에서 가장 유용한 부분

"키워드 일치가 아니라 의미로 씁니다. '장뇌삼이 포함되어야 한다' 가 아니라 '최소 두 가지를 언급해야 한다'. 답변 문구는 매번 달라지니 judge 가 판단할 여지를 남깁니다."

"실제 데이터에서 정답을 가져와야 합니다. 지어낸 정답으로 채점하면 회귀 테스트가 아니라 오답 고정입니다."
