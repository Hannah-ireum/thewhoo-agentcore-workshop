# 실서비스에 적용하려면

*— 워크샵 범위 밖에서 추가로 준비할 5가지*

이 워크샵에서 만든 것은 **레퍼런스 구현(PoC)** 입니다. 더후(The History of Whoo) 서비스에 실제로 적용하려면 아래 5가지를 별도로 설계·구축해야 합니다. 각 항목은 **워크샵에서 무엇으로 대체했는지 → 실서비스에서 무엇이 필요한지** 순으로 정리했습니다.

## 1. 실제 상품 DB / OMS 연동

**워크샵에서는**: Mock Lambda 4종 (`product_search`, `recommend_products`, `check_stock`, `get_promotion`)이 인메모리 JSONL 29개를 반환합니다.

> ⚠️ **샘플 데이터는 실제 제품 정보가 아닙니다.** `data/beauty_products.jsonl` 의 가격·전성분·평점·리뷰는 실습용으로 임의 작성한 값입니다. 제품명·라인 체계만 실제 브랜드를 참고했습니다. 화장품은 **전성분·기능성 표기가 화장품법 규제 대상**이므로, 실서비스에서는 반드시 공식 제품 정보(PIM/상품 DB)로 교체하고 법무·규제 검토를 받으세요.

**실서비스에서 필요한 것**:

- 사내 상품 DB (DynamoDB / RDS / 기존 상품 API)와의 연동
- 응답 스키마 매핑 (내부 스키마 ↔ Gateway OpenAPI 스키마)
- 인증 경로 설정: VPC Endpoint, PrivateLink, 또는 API Gateway + API Key
- 타임아웃·재시도·circuit breaker 정책
- OMS(주문관리시스템)와의 재고·배송 실시간 조회

> **대체 방법**: Lab 3의 Gateway target을 Lambda 대신 **API Gateway / HTTP URL**로 교체하면 기존 내부 API를 그대로 붙일 수 있습니다. 에이전트 코드는 변경 불필요.

### 1-a. Neptune 상품 속성 그래프 연동

GS의 상품 속성 데이터가 **Amazon Neptune**(그래프 DB)에 있다면, 관계 기반 쿼리("이 제품과 함께 구매되는 상품", "같은 성분 카테고리의 대체재")를 자연스럽게 처리할 수 있습니다.

**연동 패턴**: Neptune에 직접 붙지 않고, Lambda를 래퍼로 두고 Gateway target에 등록합니다.

```
Agent ─► Gateway ─► Lambda(Neptune 쿼리 래퍼) ─► Neptune
                        │
                        └ Gremlin / openCypher 쿼리 실행
```

**고려 사항**:

- **쿼리 언어 선택**: Neptune은 Gremlin·openCypher·SPARQL 셋 다 지원. 팀이 익숙한 언어로
- **VPC 내 접근**: Neptune은 VPC-only. Lambda를 같은 VPC에 두고 Neptune 보안그룹에서 Lambda 서브넷 허용
- **IAM 데이터베이스 인증**(선택): signed request로 Neptune 접근
- **도구 디자인**: 단일 `graph_query` 도구보다 의도별(`find_similar_products`, `find_co_purchased`) 도구 여러 개가 에이전트가 선택하기 쉬움
- **응답 크기**: 그래프 쿼리 결과가 크면 JSON 직렬화 시점에 페이징·요약 필요

**예시 Lambda 래퍼 (openCypher)**:

```python
import os
from gremlin_python.driver import client
# or: from neo4j import GraphDatabase  (openCypher via bolt protocol — Neptune 지원)

NEPTUNE_ENDPOINT = os.environ["NEPTUNE_ENDPOINT"]

def lambda_handler(event, context):
    product_id = event["product_id"]
    # openCypher: 해당 상품과 "함께 구매되는" 상품 상위 5개
    query = """
    MATCH (p:Product {id: $pid})-[:CO_PURCHASED*1..2]->(rel:Product)
    RETURN rel.id, rel.name, count(*) as score
    ORDER BY score DESC LIMIT 5
    """
    # Neptune openCypher HTTPS endpoint 호출 ...
    return {"similar_products": [...]}
```

등록 후 `recommend_agent`가 "이 제품이랑 비슷한 거 추천해줘" 같은 질문에 이 도구를 선택하게 됩니다.

**워크샵 범위에 넣지 않은 이유**: Neptune VPC 설정, 쿼리 언어 선택, 데이터 로딩까지 다루면 1일 일정을 초과합니다. 기존 Neptune이 있다면 Gateway target 하나만 추가하면 되므로, 워크샵 이후 **1-2일 내 확장 가능**합니다.

## 2. 다국어 · 경어체 규칙 · 브랜드 톤 가이드

**워크샵에서는**: 기본 한국어 존댓말, 단순한 섹션 구분만.

**실서비스에서 필요한 것**:

- 브랜드 보이스 가이드 (친근 vs 격식, 이모지 사용 기준, 호칭 "고객님/회원님")
- 금지 표현 목록 (경쟁사 언급, 특정 연예인 언급 등)
- 연령대별 톤 조정 (10대 vs 40대+ 대응)
- 다국어 지원 (영어·중국어 고객 대응 여부)
- 상담사 인수인계 기준 (어떤 질문에서 사람 상담으로 전환할지)

> **대체 방법**: Summary Agent의 system prompt를 **브랜드 톤 문서 기반으로 상세화**하고, 다국어는 System prompt `{locale}` 변수화 + 언어 감지로 분기.

## 3. 가격/프로모션 실시간성

**워크샵에서는**: `get_promotion` Lambda가 4개 고정 프로모션을 하드코딩 반환.

**실서비스에서 필요한 것**:

- 프로모션 엔진 API 연동 (카테고리·브랜드·고객 등급·시간대별 분기)
- 응답 캐시 TTL 설계 (초 단위로 바뀌는 flash sale 고려)
- 이벤트 기반 캐시 무효화 (프로모션 시작/종료 webhook)
- 응답에 **"조회 시각"** 명시 (고객이 "이거 맞아?" 할 때 대응)
- 가격 변경 시 과거 답변의 유효성 표시 방법

> **대체 방법**: Gateway target 응답 헤더에 `Cache-Control`, `X-Generated-At`을 추가하고 Summary Agent가 응답에 "현재 X시 기준"을 포함하도록 prompt에 명시.

## 4. 재고 · 배송 · 결제까지의 업무 시스템 연동

**워크샵에서는**: `check_stock`이 재고 여부와 ETA까지만 반환. 장바구니·결제·배송추적은 범위 밖.

**실서비스에서 필요한 것**:

- 장바구니 담기 기능 (사용자 세션과 장바구니 시스템 연결)
- 결제 플로우 인계 (Agent가 결제 UI로 deep-link 제공)
- 주문 상태 조회 ("배송 어디쯤이에요?")
- 반품·교환 요청 접수
- **Agent가 "어디까지" 수행할지에 대한 정책 결정** — 특히 결제 직전은 사람 확인/UI 이동이 안전한 경계

> **대체 방법**: Gateway에 `add_to_cart`, `get_order_status` 등 **상태 변경 툴**을 추가할 때는 반드시 **human-in-the-loop 확인 UX**를 동반. AgentCore Identity로 사용자 OAuth 토큰을 전달받아 행위의 주체성 확보.

## 5. 개인정보 · PII 마스킹, 금칙어, 의료 표현 가드레일

**워크샵에서는**: Lab 8 AgentCore Evaluations 의 골든셋으로 의료 표현 케이스만 기본 검증.

**실서비스에서 필요한 것**:

- **PII 마스킹**: 사용자가 실수로 주민번호·카드번호·전화번호를 보내면 로그에서 마스킹, 모델에 전달 전 삭제
- **화장품법 준수**: "치료", "완치", "의학적 효능" 등 표현 금지 (식약처 규제)
- **민감 피부 고민**: 의료 상담으로 오인될 여지가 있는 질문("이거 아토피에 써도 돼?") → 면책 문구 + 피부과 상담 권유
- **Bedrock Guardrails** 또는 별도 필터 레이어 구축 — 입력/출력 양쪽에
- **로깅 정책**: CloudWatch에 저장되는 prompt·completion에 PII가 남지 않도록
- **감사 로그** (누가 언제 무엇을 물어봤고 모델이 뭐라 답했는지)

> **대체 방법**:
> 1. Runtime 앞단에 **PII 탐지 Lambda**를 두어 입력 필터링
> 2. AgentCore에 **Bedrock Guardrails** 연결 (입·출력 동시 검증)
> 3. Evaluations에 "가드레일 케이스 50문항" 별도 골든셋 추가, CI에 연결

## 6. AgentCore Optimization — 프롬프트 개선과 A/B 테스트 자동화

**워크샵에서는**: 프롬프트를 수동으로 수정하고 골든셋으로 전후를 비교합니다.

**실서비스에서 필요한 것**: 프롬프트 변경이 쌓이면 "이게 더 나은가?" 를 체계적으로 검증하는 수단이 필요합니다. AgentCore Optimization (GA) 이 세 가지 기능을 제공합니다.

**Recommendations**: 기존 에이전트의 trace 를 분석해 시스템 프롬프트와 도구 설명의 개선안을 자동으로 제안합니다. 수동으로 "프롬프트가 왜 이런 결과를 내는지" 추측하는 대신, judge LLM 이 실제 실행 패턴을 보고 구체적인 문구 수정안을 제시합니다.

**Configuration Bundles**: 시스템 프롬프트·도구 목록·모델 설정을 하나의 **불변 버전 스냅샷**으로 저장합니다. 번들에는 ID 와 버전이 붙어서 "v3 로 롤백" 같은 운영이 가능하고, A/B 테스트의 두 대상(A안·B안)을 각각 번들로 정의합니다.

**A/B Testing**: Gateway 가 들어오는 트래픽을 두 번들 사이에서 **자동으로 분배**합니다 (비율 설정 가능). AgentCore Evaluations 가 두 경로의 점수를 각각 측정하므로, 충분한 트래픽이 쌓이면 Evaluations 결과로 승자를 판정하고 100% 전환하면 됩니다. 수동 트래픽 조작 없이 Gateway 설정 하나로 운영됩니다.

> AgentCore Optimization 공식 문서: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/optimization.html
