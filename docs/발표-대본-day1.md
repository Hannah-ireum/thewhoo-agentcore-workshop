## Pre-Lab. 인프라 셋업 (15분)

> 여기는 개념보다 **순서**가 중요합니다. 순서를 어기면 나중에 권한 에러로 막히는데, 원인을 찾기가 정말 어렵습니다. 그래서 세 단계를 반드시 순서대로 진행하겠습니다.

### 1단계 — SageMaker Studio 도메인

> 첫 번째, SageMaker Studio 도메인을 만듭니다. 왜 이걸 가장 먼저 하는지 말씀드리면 — 도메인을 만들 때 `AmazonSageMaker-ExecutionRole` 이라는 IAM role 이 **자동으로 생성**됩니다.
>
> 3단계에서 이 role 에 Bedrock 권한을 붙일 건데, 도메인이 없으면 **붙일 role 자체가 없습니다.** 그러면 권한 스크립트가 "role 이 없습니다" 하고 조용히 끝나버립니다. 에러도 안 납니다. 그리고 나중에 Lab 실행할 때 AccessDenied 를 만나게 됩니다.
>
> Console 에서 SageMaker AI → Studio → Create domain → Quick setup 으로 만들어 주세요.

> 여기서 팁을 드리면 — **기다리지 마시고 바로 다음 단계로 가세요.** 도메인이 만들어지는 데 3~5분 걸리는데, 그 사이 CloudShell 에서 인프라를 배포하면 시간이 겹칩니다.

### 2단계 — CloudShell

> 두 번째, CloudShell 에서 인프라를 배포합니다.
>
> 그 전에 자주 나오는 질문을 미리 답하겠습니다. "왜 CloudShell 과 Code Editor 를 둘 다 쓰나요? 같은 스크립트를 두 번 돌리는 건가요?"
>
> 아닙니다. **역할이 완전히 다릅니다.** 겹치는 건 `git clone` 뿐인데, 그건 서로 다른 머신이라 각자 코드를 받아야 하기 때문입니다.

[비교표를 띄운다]

> CloudShell 은 권한이 넓습니다. Admin 급 role 로 동작해서 IAM·CloudFormation·Lambda 를 만들 수 있습니다. 대신 디스크가 1GB 입니다.
>
> Code Editor 는 반대입니다. 디스크는 5GB 로 넉넉하지만 실행 role 이 제한적이라 Bedrock 호출이 막혀 있습니다.
>
> 그래서 **CloudShell 을 건너뛸 수 없습니다.** 인프라 생성 스크립트는 SageMaker role 을 감지하면 스스로 종료합니다. 어차피 권한이 없어서 실패할 걸 아니까요. 그리고 권한 부여 스크립트는 Code Editor 안에서 돌릴 수 없습니다. SageMaker role 에 붙는 `AmazonSageMakerFullAccess` 가 **`iam:PutRolePolicy` 를 주지 않기 때문**입니다. 권한 자체가 없으니, 권한이 더 큰 CloudShell 에서 해줘야 합니다.
>
> 반대로 **Code Editor 도 건너뛸 수 없습니다.** CloudShell 디스크가 1GB 라 Python 의존성 설치가 용량 부족으로 실패합니다.

> `onestop.sh` 를 실행하면 10분 정도 걸리고, 마지막에 **KB_ID** 가 출력됩니다. 이 값을 꼭 기억해 두세요. Code Editor 에서 씁니다.
>
> 이어서 권한 부여 스크립트를 실행합니다. 출력에 **"정책 적용 완료"** 가 보여야 정상입니다. 만약 "execution role 이 없습니다" 가 나오면 1단계 도메인이 아직 안 끝난 겁니다. InService 를 확인하고 다시 실행하세요.

### 3단계 — Code Editor

> 세 번째, Code Editor 입니다. Studio 를 열고 Applications → Code Editor → Create Code Editor space → Run space → Open 순서로 진행합니다. 설정은 기본값 그대로 두시면 됩니다.
>
> 터미널을 열고 clone 과 셋업을 하는데, **여기서 오늘 가장 중요한 한 줄**이 나옵니다.

[화면에 `source .venv/bin/activate` 를 강조해 띄운다]

> `setup-python.sh` 는 가상환경을 **만들어 주지만 활성화까지 이어지지 않습니다.** 스크립트는 자식 프로세스라서, 그 안에서 활성화해도 스크립트가 끝나면 사라집니다. 그래서 여러분이 직접 `source` 를 해야 합니다.
>
> 이걸 빠뜨리면 Lab 1 부터 이런 에러가 납니다.

[에러 메시지를 띄운다]

```
ImportError: cannot import name 'CacheConfig' from 'strands.models.model'
  (/opt/conda/lib/python3.12/site-packages/strands/models/model.py)
```

> **판별법을 기억하세요. 에러 경로에 `/opt/conda` 가 보이면 venv 문제입니다.** Code Editor 에 미리 깔린 구버전 라이브러리를 쓰고 있다는 뜻입니다. `source .venv/bin/activate` 하고 다시 실행하면 됩니다.
>
> 그리고 **터미널을 새로 열 때마다** 다시 해야 합니다. 프롬프트 앞에 `(.venv)` 가 보이면 활성화된 상태입니다.

## Lab 0. 데이터 준비하기 (30분)

> 이제 지식창고, Knowledge Base 를 만듭니다. 핵심 요소가 세 개입니다 — **S3 원본, Embedding 모델, Vector store.**
>
> 이 셋에서 **dimension 이 정확히 일치**해야 합니다. 우리는 Titan Embed v2 를 쓰고 1024 차원입니다. 모델을 바꾸면 이 숫자도 바뀌고, KB 를 만든 뒤에는 변경이 안 돼서 재생성해야 합니다.
>
> 그런데 오늘 진짜 배우실 건 **chunking 전략**입니다. 이게 검색 품질의 80% 를 결정합니다.

### chunking 을 왜 NONE 으로 했나

> 우리는 상품 하나당 파일 하나로 쪼개고, chunking 전략을 `NONE` 으로 뒀습니다. 자르지 않는다는 뜻이죠. 왜 그럴까요?
>
> 상품 하나가 이미 **자연스러운 의미 단위**이기 때문입니다. 이름, 성분, 사용법, 가격이 한 묶음이잖아요. 이걸 300 토큰 단위로 인위적으로 자르면 성분 목록 절반이 다른 chunk 로 갈립니다. 오히려 품질이 떨어집니다.
>
> 그리고 결정적인 이유가 하나 더 있습니다. 만약 29개 상품을 JSONL 파일 하나에 다 넣고 `NONE` 을 쓰면 어떻게 될까요?
>
> **chunk 가 1개가 됩니다.** top-3 를 요청해도 같은 덩어리가 세 번 나옵니다. 이게 실무에서 자주 하는 실수입니다.

[`count-categories.py` 실행]

> 스킨케어 12, 메이크업 8, 바디 4, 헤어 3, 향수 2 — 총 **29개 상품**입니다.
>
> Ingestion 이 끝나면 `status=COMPLETE`, `Scanned=29`, `Indexed=29` 가 나와야 정상입니다.

[`pretty-retrieve.py "천기단 복합 성분"` 실행]

> 자, 여기를 보세요. **서로 다른 상품 3개**가 관련도 0.7 대로 나왔습니다.
>
> 두 가지를 확인하시면 됩니다. 첫째 서로 **다른** 상품이 나왔다는 것 — chunking 이 제대로 됐다는 증거입니다. 둘째 점수가 0.5 이상이라는 것. 만약 0.3 이하가 나오면 쿼리와 데이터의 언어가 다른 경우가 많습니다. 영어로 물었는데 한국어 데이터인 경우죠.

## Lab 1. 상품 정보를 이해하고 답하는 챗봇 (45분)

> Strands Agent 의 핵심은 딱 세 가지입니다 — **model, system_prompt, tools.** 이 세 줄이 에이전트의 전부입니다.
>
> 그리고 오늘 가장 중요한 개념이 여기 있습니다. **에이전트는 도구를 언제 쓸지 스스로 판단합니다.** 우리가 if-else 로 정해주지 않습니다.
>
> 그럼 무엇을 보고 판단할까요?

### docstring 이 곧 명세다

[`@tool` 데코레이터가 붙은 `kb_retrieve` 코드를 띄운다]

> **docstring 입니다.** `@tool` 데코레이터로 함수를 등록하면, 이 docstring 이 LLM 에게 전달되는 **유일한 설명서**가 됩니다.
>
> 그래서 docstring 은 주석이 아니라 **인터페이스 명세**입니다. 여기를 모호하게 쓰면 엉뚱한 도구를 부릅니다. 실무에서 "에이전트가 도구를 잘못 골라요" 라는 문제의 80% 는 description 문제입니다.

[`python run_lab1.py` 실행]

> 성분과 사용법이 섹션으로 나뉘어 답변됐습니다. 여기서 중요한 건 이 내용이 **KB 에서 온 것**이라는 점입니다. 천기단 복합 성분, 장뇌삼, 영지, 청아교 — 전부 실제 데이터에 있는 값입니다.

### 이 Lab 의 하이라이트 — 한계 확인

> 이제 일부러 **못 하는 걸** 시켜 보겠습니다. 오늘 Lab 1 의 핵심 학습 포인트입니다.

[`python run_lab1.py "천기단 화현 크림 재고 있어?"` 실행]

> "재고 정보는 확인할 수 없습니다" 라고 답했습니다.
>
> **실패한 것처럼 보이지만, 이게 정상이고 오늘 가장 중요한 장면입니다.**
>
> 왜 중요한가요? 나쁜 에이전트는 여기서 **지어냅니다.** "재고 3개 남았습니다" 라고요. 데이터에 없는데도 그럴듯하게 만들어냅니다. 그게 실서비스에서 사고가 됩니다.
>
> 우리 에이전트는 "내 지식 범위 밖" 이라고 정직하게 말합니다.
>
> 그럼 왜 KB 에 재고를 안 넣었을까요? **재고는 실시간으로 바뀌는 값**입니다. KB 에 넣으면 어제 값으로 "재고 있습니다" 라고 답합니다. 오히려 독이 되죠.

[정보 3분류 표를 띄운다]

> 그래서 정보를 성격에 따라 세 곳에 나눠 저장합니다.
>
> **정적인 정보** — 성분, 사용법, 가격. 이건 Knowledge Base 에. 오늘 Lab 1 에서 했습니다.
>
> **실시간 정보** — 재고, 프로모션. 이건 외부 API 를 Lambda 로 감싸서 Gateway 에. Lab 3 에서 합니다.

>
> 지금 정적 칸을 채웠고, 나머지 두 칸이 비어 있는 상태입니다.
>
> 여러분 도메인에 적용하실 때도 이 3분류를 먼저 하시면 좋습니다. **KB 에 다 넣지 마세요.** 업데이트 주기가 일주일 이상인 것만 KB 후보입니다.

## Lab 2. 대화 맥락을 기억하기 (45분)

> 지금 챗봇은 대화가 끝나면 다 잊습니다. "저번에 추천한 거" 를 모릅니다. AgentCore Memory 를 붙이겠습니다.
>
> 그런데 Memory 가 하나가 아니라 **4가지 종류**가 있습니다. 왜 나눴을까요? **읽는 시점이 다르기 때문**입니다.

[4-strategy 표를 띄운다]

> **UserPreference** — 피부타입, 선호. 세션 시작할 때 한 번 읽습니다.
>
> **Summary** — 이번 대화 요약. 재접속할 때 유용하죠.
>
> **Semantic** — 도메인 사실과 지식. 관련 질문이 나올 때만 읽습니다.
>
> **Episodic** — 상담 에피소드. "저번에", "그거" 같은 모호한 참조를 해결할 때 씁니다.
>
> 왜 이렇게 나눌까요? **전부 매 턴 조회하면 context window 가 낭비되고 비용도 늘기 때문입니다.** 필요한 것만 필요한 시점에 가져오는 게 설계 포인트입니다.
>
> namespace 를 보시면 의도가 드러납니다. UserPreference 는 `/preferences/{actorId}/` — sessionId 가 없습니다. 세션을 넘어 누적된다는 뜻이죠. Summary 는 `/summaries/{actorId}/{sessionId}/` — 세션별로 분리됩니다.

[`create-memory.py` 실행 — 수 분 걸림]

> 이 스크립트는 strategy 4개가 ACTIVE 될 때까지 기다리므로 몇 분 걸립니다. 그 사이 방금 설명한 4가지를 다시 정리하겠습니다.

### 꼭 알아야 할 특성 — eventual consistency

> 여기서 반드시 아셔야 할 게 하나 있습니다. **장기 메모리 추출은 eventual consistent 입니다.**
>
> 이벤트를 저장한 직후에 조회하면 안 나옵니다. 그래서 실습에서 seed 를 넣고 **60초 대기**합니다.
>
> 실서비스에서도 "저장했으니 바로 읽힌다" 고 가정하면 안 됩니다. "방금 저장한 게 안 읽힌다" 는 이슈가 여기서 옵니다.

[`run_lab2.py seed` → 60초 → `ask "보습크림 추천해줘"` 실행]

> 답변을 보세요. 제가 질문에 "건성" 이나 "민감성" 이라고 **한 마디도 안 했습니다.** 그런데 답변이 민감 피부용 제품을 우선 추천하고 "자극 최소화" 를 언급합니다.
>
> seed 로 저장한 프로필을 Memory 에서 읽어온 겁니다. 이게 개인화입니다.

## Lab 3. 외부 도구 연결하기 (60분)

> Lab 1 에서 못 답했던 재고 질문, 이제 해결합니다.
>
> 방법이 두 가지 있습니다. 첫째 `@tool` 로 직접 감싸기 — Lab 1 의 `kb_retrieve` 가 그 방식이었죠. 둘째 Gateway 에 등록하기. 그럼 왜 Gateway 를 쓸까요?

### Gateway 를 쓰는 판단 기준

> **도구가 3개 이상이거나 / 여러 에이전트가 같은 도구를 공유하거나 / inbound 인증이 필요하면 Gateway 입니다.**
>
> `@tool` 방식은 간단하지만, 도구가 20개로 늘면 에이전트 코드에 boto3 호출이 20개 박힙니다. 인증도 각각 관리해야 하죠.
>
> Gateway 는 "**MCP 서버에 붙기**" 하나만 알면 됩니다. 백엔드가 Lambda 든 온프렘 API 든 Gateway 가 차이를 흡수합니다.
>
> 그리고 Gateway 의 핵심 가치가 하나 더 있습니다. **인증 경계 분리**입니다. 사용자에서 Gateway 로 오는 inbound 와, Gateway 에서 백엔드로 가는 outbound 를 분리해서 강제합니다. 워크샵은 inbound 를 NONE 으로 두지만, **운영에서는 반드시 JWT 를 쓰셔야 합니다.**

[`create-gateway.py` 실행 → target 4개 READY 확인]

> Gateway 1개와 Lambda target 4개가 만들어졌습니다. 4개 모두 READY 인지 확인하세요.
>
> 여기서 `toolSchema` 가 중요합니다. 특히 `description` 한 줄이 **Agent 의 도구 선택 정확도를 거의 결정**합니다. "언제 이 도구를 쓰는지" 를 구체적으로 써야 합니다.

[`run_lab3.py "WHOO-00101 재고 있어?"` 실행]

> `[도구 호출 내역]` 블록을 보세요.

```
→ check-stock___check_stock  {"product_id": "WHOO-00101"}
← result [success]  available=True, eta=2~3일 이내 도착
```

> 여기가 핵심입니다. 제가 "재고를 확인해라" 라고 코드에 쓴 게 아닙니다. 에이전트가 질문을 보고 **4개 도구 중 `check_stock` 을 골랐고**, `WHOO-00101` 을 인자로 뽑아냈습니다.
>
> 그리고 도구 이름을 보세요. `check-stock___check_stock` — 밑줄 세 개로 연결돼 있습니다. Gateway 가 **target 이름을 prefix 로 붙여서** 노출하기 때문입니다. 그래서 system prompt 에도 이 전체 이름을 적어야 합니다. 짧은 이름으로 부르면 "tool not found" 가 나고 재시도가 발생합니다.

[`run_lab3.py "민감성에 진정 좋은 거 추천하고 프로모션도 알려줘"` 실행]

> 이번엔 도구를 **두 개 연달아** 불렀습니다. 추천하고, 프로모션 조회하고, 결과를 합쳐서 답했죠.
>
> 우리가 "이 순서로 불러라" 고 코딩한 게 아닙니다. LLM 이 description 을 보고 스스로 판단한 겁니다.
